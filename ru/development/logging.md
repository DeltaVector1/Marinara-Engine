# Журналирование сервера

Страница объясняет чтение серверного журнала Marinara Engine и написание полезных записей. Она дополняет [раздел Logging в CONTRIBUTING.md](../../CONTRIBUTING.md#logging), не заменяя его. Общий Pino logger, объект ошибки первым аргументом, спецификаторы формата и таблица четырех уровней остаются обязательными.

<a id="what-every-line-carries"></a>

## Содержимое каждой строки

Все серверные строки создаются одной инстанцией Pino: `logger` в `packages/server/src/lib/logger.ts`. Fastify использует ее через `loggerInstance`, поэтому `req.log`, `reply.log` и `app.log` являются дочерними. У них общие сериализаторы и горячие обновления `LOG_LEVEL` из наблюдателя окружения.

| Поле | Где | Значение |
| --- | --- | --- |
| `pid` | каждая строка | ID процесса (стандарт Pino). |
| `hostname` | каждая строка | Имя хоста (стандарт Pino). |
| `bootId` | каждая строка | 8 шестнадцатеричных символов, новые при каждом запуске. Различают запуски в общем файле. |
| `requestId` | каждая строка, вызванная запросом | Значение заголовка ответа `x-request-id`. Есть и в `req.log`, и в общем `logger` внутри служб. |
| `route` | после разбора тела | Совпавший шаблон маршрута, например `/api/chats/:id`. Никогда не сырой URL. |

<a id="request-ids"></a>

### Идентификаторы запросов

`lib/request-logging.ts` назначает каждому запросу ID:

- Клиент может передать `x-request-id`. Сервер сохраняет 8–80 символов из `A-Z a-z 0-9 . _ : -`; остальные значения заменяет.
- Иначе сервер создает UUID. Счетчик Fastify `req-1` начинался заново при каждом запуске, повторяя ID.
- ID возвращается в доступном через CORS заголовке `x-request-id`. Его можно указать в отчете, а `grep <id>` найдет все строки запроса.

ID хранится в контексте `AsyncLocalStorage` (`lib/log-context.ts`). Примесь Pino копирует его в каждую строку. Передавать его вручную не нужно: `logger.warn(err, "...")` глубоко в службе получает его автоматически. После разбора тела контекст задается вновь, поскольку HTTP-парсер разбирает тело в собственном асинхронном контексте.

Контекст сопровождает всё, что запускается внутри запроса, включая таймеры, обработчики и дочерние процессы. Начало работы, переживающей запрос, оборачивают в `runWithRootLogContext({}, fn)`, чтобы поздние строки не носили исходный ID. Локальный вспомогательный процесс делает это для llama-server и MLX; Decision и Utility запускаются так же, чтобы процесс, общий для последующих запросов, не сохранял ID первого клиента. Другая долгоживущая работа из обработчика маршрута продолжает носить его `requestId`, пока не получит такую же обертку.

<a id="request-lines"></a>

### Строки запросов

`RequestLogController` использует стандартный `LogController` Fastify со следующими изменениями:

- Поле называется `requestId`, а не `reqId`. Сохраненные поиски и фильтры по `reqId` требуют нового имени.
- Строки `incoming request` и `Route ... not found` не включают параметры запроса: там могут быть токен или текст поиска. Входящая строка сохраняет остальные поля `req` (`method`, `version`, `host`, `remoteAddress`, `remotePort`) и добавляет `route`.
- Если клиент преждевременно закрыл запрос, пишется одна строка `Client aborted request` на info. Fastify здесь ничего не писал.

`LOG_DISABLE_REQUEST_LOGGING` работает как прежде и отключает также строку отмены.

В `pnpm dev` pino-pretty скрывает `hostname` (по умолчанию) и `bootId`. Производственный JSON сохраняет оба.

<a id="startup-timeline"></a>

## Хронология запуска

`lib/startup-timeline.ts` измеряет каждый этап:

```ts
const db = await startup.phase("storage.open", () => getDB());
```

- Каждая строка содержит `event: "startup.phase"`, `stage`, `elapsedMs` (прошедшее время) и `selfMs` (собственное время без вложенных фаз). Уровень зависит от `selfMs`: debug ниже 1 с, info выше 1 с, warn выше 15 с. При стандартном `LOG_LEVEL=warn` обычный запуск, даже медленный первый, не печатает фазы.
- Фазы вложены. `app.build` в `index.ts` охватывает фазы `buildApp`. Благодаря `selfMs` медленный внутренний шаг сообщает о себе один раз; `app.build` остается debug, если его собственная работа вне вложенных фаз не медленная.
- Ошибка шага не записывается внутри фазы. Она без изменений поднимается выше; `main().catch` в `index.ts` пишет одну строку `startup.failed` с именем шага (`startup.stageOf(err)`).
- После начала прослушивания `index.ts` пишет одну info-строку `[startup] Ready in N ms` с `event: "startup.ready"`, числом фаз и пятью шагами с наибольшим `selfMs`.

Фазы не добавляют `stage` в контекст журнала. Запущенные внутри службы сохраняют таймеры, которые иначе носили бы имя этапа всю жизнь процесса.

<a id="one-line-per-failure"></a>

## Одна строка на сбой

Сбой должен давать ровно одну строку, написанную кодом, определяющим дальнейшее поведение.

- **Записать или бросить дальше, не оба действия.** При повторном выбрасывании журналирует вызывающий код. Полезные детали идут в debug, например имя инструмента в `[agent-tools] ... failed`.
- **Где пишется строка:**
  - неизвестные 500: `middleware/error-handler.ts`
  - ошибки агентов: `executeAgent` (warn, некритический сбой)
  - неудачная генерация чата: основной catch в `generate.routes.ts`
  - Соответствующий провайдер бросает ошибку без записи. Максимум добавляет debug с моделью и сырой ошибкой, как Grok CLI и Claude (Subscription). Claude (Subscription) бросает понятное сообщение, уже содержащее ошибку SDK, поэтому не присоединяет ее также как `cause`. Ошибка SSE чата и текст ошибки агента дописывают сообщение причины и иначе показали бы его дважды.
- **Отмены имеют уровень info.** Остановка пользователем, закрытая вкладка или отмененный сигнал ожидаемы. Используйте `failureLevel(err)` либо `failureLevel(err, "warn")` из `lib/log-context.ts`. При истинном `isCancellation(err)` возвращается `"info"`. `TimeoutError` является настоящим сбоем, а не отменой.

  ```ts
  logger[failureLevel(err)](err, "[agent-batch] Batch call FAILED: %s", errMsg);
  ```

- **Сохраняйте причину.** Оборачивайте в `new Error("Could not save chat", { cause: err })`. Сериализаторы `err` и `error` добавляют сообщение и стек причины (`caused by: ...`). Error, записанный как `{ error }`, тоже сериализуется и больше не выводится как `{}`.

<a id="repeating-failures"></a>

## Повторяющиеся сбои

Опросы, проверки работоспособности и хуки каждого хода могут одинаково сбоить раз в несколько секунд. Используйте `logRateLimited` из `lib/log-rate-limit.ts`:

```ts
logRateLimited("warn", "autonomous-scheduler:poll", err, "[autonomous-scheduler] Poll failed");
```

Первое появление ключа записывается. Следующие в окне (по умолчанию 60 с) подсчитываются; следующая строка содержит `suppressedRepeats`. Включайте в ключ проблемный объект, например ID пакета или чата, чтобы одна неисправность не скрывала другую.

<a id="prompt-and-model-text"></a>

## Текст промпта и модели

Промпты, вывод модели, тела ответов провайдера и опросов идут на **debug**, никогда warn или error. Они могут содержать историю пользователя, а ответы провайдера – повторять учетные данные или промпт. На warn записывайте размер (`rawLength`, `bodyLength`) и причину. Ошибка разбора JSON может цитировать исходный текст, поэтому на warn сохраняйте только тип ошибки. Саму ошибку и текст помещайте в отдельную debug-строку:

```ts
logger.warn(
  { errorType: err instanceof Error ? err.name : typeof err, rawLength: raw.length },
  "[game/scene-wrap] Failed to parse LLM response as JSON",
);
logger.debug({ err }, "[game/scene-wrap] Unparsed LLM response: %s", raw.slice(0, 200));
```

Переключатель отладки интерфейса работает через `logDebugOverride`. Это предусмотренный способ видеть промпты, когда `LOG_LEVEL` скрывает debug.
